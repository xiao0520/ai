## 2. 看配置、日志

在服务器用 `cat 文件名` 查看、`vi 文件名` 修改。Docker 运行配置入口是 `/opt/mjn-ai/docker/current/compose.json`。Java/Python 共用 `/etc/mjn-ai/config.env`，每次容器重启都会重新读取，无需 `source`。修改 MySQL、Redis、Kafka 或 Nginx 的容器配置后，需重建对应容器才能确保重新挂载配置；日常重启用第 3 节命令即可。


### 生成 SHA256SUMS，再上传

**执行顺序：打包成功 → 本地生成 SHA256SUMS → 上传包和 SHA256SUMS → 服务器校验 → 部署。**

SHA256SUMS 是下面命令生成的文件，不会由 Maven、pnpm 或 tar 自动生成。它记录本次发布包的 SHA256，用于确认上传前后的文件一致；每次重新打包后都要重新生成。

**在本地 Windows PowerShell 执行：**

```powershell
cd "D:\project\.mjn-build-temp\packages"
$files = "ruoyi-admin.jar","ai-service.tar.gz","admin.tar.gz","web.tar.gz"
$lines = foreach ($file in $files) { (Get-FileHash $file -Algorithm SHA256).Hash.ToLower() + "  " + $file }
[IO.File]::WriteAllText("D:\project\.mjn-build-temp\packages\SHA256SUMS", ($lines -join "`n") + "`n", [Text.UTF8Encoding]::new($false))
```

生成位置：`D:\project\.mjn-build-temp\packages\SHA256SUMS`。该文件使用 Linux 可识别的 LF 换行。

**只更新一个包时**，将上面 `$files` 那一行替换为对应文件名，其余命令不变。例如只更新 Java：

```powershell
$files = "ruoyi-admin.jar"
```

先把本次新 JAR 复制到 packages 目录再生成校验文件，不要对旧包生成校验。IDEA 打包后可执行：

```powershell
Copy-Item "D:\project\mjn-ai\main-service\ruoyi-admin\target\ruoyi-admin.jar" "D:\project\.mjn-build-temp\packages\ruoyi-admin.jar" -Force
```

用已有服务器文件窗口，将**本次发布包和新生成的 SHA256SUMS 一起上传**到 `/opt/mjn-ai/packages/`，覆盖旧的同名文件。单包发布也要上传对应的新校验文件。

上传后在服务器执行：

```bash
cd /opt/mjn-ai/packages
sha256sum -c SHA256SUMS
```

清单内所有文件均显示 `OK` 后再部署。校验失败时检查上传文件，不要在服务器重新生成校验文件。

| `knowledge.ingestion.command.v1` | Java → Python | INGESTION / REBUILD 调度 |
| `knowledge.job.result.v1` | Python → Java | STARTED / PROGRESS / FAILED / CANCELLED / ARTIFACTS_READY |
| `knowledge.job.control.v1` | Java → Python | 取消广播 |
| `knowledge.dlq.v1` | 双端 → 运维 | 无法继续处理的消息摘要与原因 |

开发机默认由 Java 创建四个 Topic，每个 3 分区、1 副本。共享或生产环境必须按容量和可用性重新确定副本数，并为 Java、Python 服务账号配置最小 Topic ACL。统一内部 HTTP 签名不写入 Kafka 消息，也不能替代 Broker TLS、账号认证和 ACL。

当前远程单节点环境关闭了自动建 Topic。2026-09-30 已手工创建上述四个 Topic，每个 3 分区、1 副本；新环境首次启动 Python Kafka Worker 前先确认这四个名称都存在。单节点补建命令如下，已有 Topic 会跳过：

```bash
for topic in knowledge.ingestion.command.v1 knowledge.job.result.v1 knowledge.job.control.v1 knowledge.dlq.v1; do
  docker exec mjn-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server 127.0.0.1:59092 --create --if-not-exists --topic "$topic" --partitions 3 --replication-factor 1
done
docker exec mjn-kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server 127.0.0.1:59092 --list
```

### 7.2 启用顺序

以下步骤保留为全部 RAG 功能完成后的统一联调与验收操作清单，当前开发阶段不执行真实环境验收。

1. 备份目标数据库，在升级 Java 前依次执行 main-service/docs/script/sql/knowledge-kafka-v1.sql、knowledge-document-model-profiles-v1.sql、knowledge-artifact-publication-v1.sql 和 knowledge-multimodal-artifacts-v1.sql。四个脚本都支持重复执行；后两个脚本新增不可变产物批次、索引成员及视觉向量维度/数量字段。
2. 启动 Kafka 和 Qdrant，确认 Java/Python 所在主机能连接 Broker，Python 所在主机能访问 Qdrant。
3. 在 Java 与 Python 环境同时配置 AI_KAFKA_ENABLED=true 和相同的 AI_KAFKA_BOOTSTRAP_SERVERS；在 Python 配置 AI_QDRANT_URL，远程 Qdrant 同时安全注入 AI_QDRANT_API_KEY。
4. 检查 Java application.yml 中的 knowledge.kafka、knowledge.worker-auth 与 Python ai-service/.env.example 中的 Topic、消费组、超时和 Qdrant 变量。
5. 配置 AI_JAVA_INTERNAL_BASE_URL，使其与 Java knowledge.worker-auth.resource-base-url 指向同一个 Worker 可访问的内部地址；内部签名密钥和服务 Token 必须由两端安全注入。
6. 在模型管理保存并发布可执行的 Vector 与 Image Profile，确认 providerCode、apiMode、模型名、凭证键、输入模态和向量维度与实际服务一致。文本向量可使用 `OPENAI_EMBEDDINGS`，方舟多模态向量使用 `ARK_MULTIMODAL_EMBEDDINGS`；视觉/OCR 模型使用 `RESPONSES` 或 `CHAT_COMPLETIONS`。
7. 重启 Python、Java，确认迁移、Topic、Listener 和消费者正常。Kafka 启用后，Python 无法连接 Broker会直接启动失败；Qdrant 或模型不可用会使对应任务返回稳定失败，不应发布索引。
8. 检查 Python /health 和 /ready，先用小型 TXT 验证 TEXT 任务，再用包含 data URI 图片的 Markdown、含图 DOCX 或扫描 PDF 验证 MULTIMODAL 任务、OCR 文本、`dense_vision`、图片来源定位、OSS 清单、索引成员及激活后的文档版本。

Python 续租间隔默认 10 秒，Java 执行租约默认 60 秒，整次执行默认 600 秒，命令有效期默认 1200 秒。调整时必须保证租约大于心跳间隔与最大网络延迟，并让命令有效期覆盖允许的排队时间。

多模态 Worker 的资源上限由 `AI_RAG_IMAGE_MAX_COUNT`、`AI_RAG_IMAGE_MAX_BYTES`、`AI_RAG_IMAGE_MAX_PIXELS`、`AI_RAG_VISION_MAX_CONCURRENCY` 和 `AI_RAG_VISION_MAX_OUTPUT_TOKENS` 控制。调整前应同时评估 Worker 内存、模型并发、费用和任务租约；Markdown 解析不会主动下载外部图片链接。

## 8. 业务 OSS 路由

各业务上传统一使用当前默认 OSS 配置。默认 OSS 配置的“前缀”是公共根目录，例如 `test`；系统参数保存该根目录下的业务子目录，不是 `sys_oss_config.config_key`。

| 业务 | 系统参数键 | 参数值 | 示例对象路径 |
|---|---|---|---|
| 模型厂商图标 | `ai.oss.provider-icon.config-key` | `provider-icon` | `test/provider-icon/{uuid}.png` |
| Skill Markdown 文档 | `ai.oss.skill-artifact.config-key` | `skill-artifact` | `test/skill-artifact/{uuid}.md` |
| 知识库附件 | `ai.oss.knowledge-attachment.config-key` | `knowledge-attachment` | `test/knowledge-attachment/{uuid}.pdf` |

上传路径不自动增加日期层级，最终路径由“默认 OSS 前缀 + 业务子目录 + 随机文件名”组成。例如默认前缀为 `test`、业务子目录为 `provider-icon` 时，结果为 `test/provider-icon/5f8e1d2c....png`。

业务参数缺失时上传接口应直接报错。无需为 `provider-icon`、`skill-artifact` 或 `knowledge-attachment` 新建同名 OSS 配置；它们是同一默认桶下的业务目录。变更默认 OSS 或这些系统参数后，应分别验证模型图标、Skill 文档和知识库附件的上传、读取及删除权限。




## 9. MCP 只读工具运行配置

当前 Java 按角色、Agent 和模型 `TOOL` 能力下发单次授权工具清单；Python 通过 Streamable HTTP 调用远端 MCP Server。管理端只填写 `credentialKey` 别名，Bearer 令牌配置在 Python 现有 `AI_PROVIDER_CREDENTIALS` 中；`NONE` 无需令牌。部署时确认 Python 能访问 Server Endpoint，并检查工具 Manifest 的 Schema、只读注解、启停、角色授权和 Agent 绑定。当前运行时不支持 STDIO、OAuth、写工具审批。

本地 Everything MCP Server 的启动、回归命令、错误码及尚未完成的真实业务联调见 [MCP 接入与验收](MCP接入与验收.md)。工具报错时先按 `TOOL_REJECTED`、`TOOL_CREDENTIAL_MISSING`、`TOOL_TIMEOUT` 区分授权/Schema、密钥别名和网络超时；不要在日志或工单复制实际令牌。
