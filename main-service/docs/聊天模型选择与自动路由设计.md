# 聊天模型选择与自动路由设计

> 最后更新：2026-09-20  
> 当前状态：`FIXED` 与 `AUTO` 均已完成代码、数据库迁移和自动化验证；真实多供应商联调仍归入最终环境验收。

## 1. 目标与边界

聊天入口支持两种互斥模式：

| 模式 | 用户行为 | 系统行为 | 状态 |
|---|---|---|---|
| `FIXED` | 选择具体模型 | Java校验权限和预算后直接调用该模型 | 已完成 |
| `AUTO` | 选择“智能选择” | Java限定候选，LangChain在候选内路由，Java复核后执行 | 已完成 |

职责保持不变：

- Java负责用户、角色模型权限、Agent约束、模型配置、会话、预算、审计和业务状态。
- Python/LangChain负责路由推理和模型执行，不连接业务MySQL，不自行扩大候选范围。
- 浏览器只访问Java；普通聊天与RAG聊天继续使用内部HTTP/SSE。
- Embedding、视觉/OCR 继续使用索引及文档处理快照，Rerank 使用知识库检索配置；它们都不参加聊天模型 AUTO 路由。

## 2. 用户侧契约

### 2.1 FIXED

```json
{
  "modelMode": "FIXED",
  "modelId": "2095429001073393665",
  "sessionId": "2097571163865210881",
  "content": "请解释这段代码"
}
```

- `modelId` 必填，必须是用户已授权且可执行的聊天模型。
- 旧客户端未传 `modelMode` 时，Java兼容为 `FIXED`。
- Python不接收 `modelMode`，只接收Java已经裁定的单个模型Profile。

### 2.2 AUTO

```json
{
  "modelMode": "AUTO",
  "modelId": null,
  "sessionId": "2097571163865210881",
  "content": "分析这个架构问题并给出代码方案"
}
```

- 不使用 `0`、`-1` 或虚假模型记录表示智能选择。
- Java先计算角色权限与Agent绑定的交集，只把可执行的精确模型修订下发给Python。
- Python使用LangChain确定性路由后，Java再次复核候选摘要、模型ID、发布修订、角色权限和Agent权限，再进入原有预算与生成链路。
- 用户端已开放“智能选择”，回答完成后展示实际使用的模型。

## 3. FIXED 实现

```text
用户选择具体模型
  → 前端发送 FIXED + modelId
  → Java校验模式和modelId
  → 校验角色模型权限、模型状态、发布修订和执行配置
  → 按该模型裁剪上下文并预占Token
  → Java向Python下发单个精确模型Profile
  → Python通过现有LangChain/Provider链生成
  → Java转发SSE、结算用量并保存实际modelId
```

已经落地：

- `ChatModelSelectionMode` 定义 `FIXED` 和 `AUTO`。
- `ChatSendBo.modelMode` 默认是 `FIXED`；FIXED缺少 `modelId` 时校验失败，AUTO允许不传 `modelId`。
- Java在权限查询、预算预占和异步执行前校验模式及最终模型。
- 前端根据选择显式发送 `FIXED + modelId` 或 `AUTO`。
- 普通聊天与RAG聊天继续复用现有权限、预算、调用、SSE和结算链路。
- Python路由、Java权限边界、前端类型与交互均已纳入自动化验证；完整结果见项目开发进度文档。

## 4. AUTO 总体流程

采用两阶段方案，先路由，再预算和生成：

```text
用户选择 AUTO
  → Java计算授权候选模型
  → Java下发不可扩大的候选快照
  → Python/LangChain选择候选模型
  → Java复核 selectedModelId + revision
  → Java按最终模型计算上下文和预占Token
  → 复用现有FIXED单模型生成链路
```

不让Python选完后直接生成，因为模型确定前Java无法准确完成权限复核、上下文裁剪、最大输出限制、Token预占和实际模型审计。

## 5. Java候选模型

Java计算以下交集：

```text
用户角色授权模型
∩ 已启用、已发布且配置完整的聊天模型
∩ 当前Agent允许使用的模型
∩ 本轮输入模态与能力要求
∩ 当前上下文长度要求
∩ 管理员允许参加自动路由的模型
```

规则：

1. 候选项使用精确 `modelId + publishedRevision`。
2. Agent场景复用已有模型绑定和选择策略，不建立第二套授权。
3. Python只能缩小Java候选范围，不能添加模型。
4. 候选为空时Java直接返回授权或配置错误。
5. 候选只有一个时直接选中，但仍记录AUTO决策。
6. 路由后模型被停用或修订变化时，Java最终复核失败并要求重试。

## 6. 模型管理路由属性

首期直接复用模型管理已有字段，不新增重复配置：

| 现有属性 | 当前用途 |
|---|---|
| `modelShow=Y` | 允许模型进入AUTO候选，同时保持用户端可见语义 |
| `capabilities` | 配置 `GENERAL/CODE/REASONING/LONG_CONTEXT/VISION/TOOL` 能力标签 |
| `maxInputTokens` | 过滤无法容纳本轮输入的模型 |
| `inputCostPerMillion` / `outputCostPerMillion` | 同能力候选的成本排序；未配置成本排在已配置成本之后 |
| `grayWeight` | 作为路由优先级，值越大越优先 |
| Agent默认模型 | Agent场景的授权兜底模型 |

首期的质量和延迟等级固定为中性值3，避免在缺少真实评测数据时制造虚假精度。管理后台聊天模型表单已开放能力标签、成本和路由优先级配置。Python只依据Java候选属性路由，不按豆包、DeepSeek等厂商名称硬编码。

## 7. LangChain路由

### 7.1 首期：确定性路由

- 使用 `RunnableLambda` 提取输入长度、模态、RAG、工具和任务类型等特征。
- 使用 `RunnableBranch` 按候选能力、策略和优先级选择模型。
- 路由契约已保留 `hasImage`；当前聊天入口仅支持文本并传 `false`，接入图片附件后由Java据实传入并只选择视觉模型。
- 长上下文问题选择能够容纳当前历史的模型。
- 代码、推理等任务使用管理员配置的能力标签。
- 普通短问题在满足能力后按成本、延迟和优先级选择。
- 无法判定时返回Java下发的授权兜底模型。

首期不调用额外模型，没有路由Token费用，规则可解释且容易验收。

### 7.2 后续：可选LLM路由

- 使用 `ChatPromptTemplate` 和结构化输出分类问题。
- 只允许返回候选中的模型ID和修订。
- 单独记录路由模型的Token、延迟和失败。
- Java对路由结果再次复核。
- 路由模型不能生成Endpoint、密钥别名或候选外模型。

## 8. Java与Python路由契约

已实现：

```text
POST /internal/ai/v1/chat/route
```

请求核心字段：

```json
{
  "requestId": "uuid",
  "candidateSnapshotHash": "64位SHA-256",
  "question": "分析这个架构问题",
  "features": {
    "ragEnabled": false,
    "hasImage": false,
    "estimatedInputTokens": 1200
  },
  "candidates": [
    {
      "modelId": "1",
      "revision": 3,
      "capabilities": ["CODE", "REASONING"],
      "maxInputTokens": 128000,
      "qualityTier": 3,
      "costTier": 2,
      "latencyTier": 2,
      "priority": 100
    }
  ],
  "policy": {
    "revision": 1,
    "strategy": "RULES",
    "fallbackModelId": "1"
  }
}
```

响应核心字段：

```json
{
  "requestId": "uuid",
  "selectedModelId": "1",
  "selectedRevision": 3,
  "reasonCode": "CODE_REASONING",
  "policyRevision": 1,
  "usage": []
}
```

要求：

- 使用现有Java/Python统一内部签名。
- 路由请求不携带候选模型API Key。
- 候选快照携带版本或摘要，防止响应与请求不一致。
- 候选外模型、错误修订或未知策略版本由Java拒绝。
- Java复核成功后继续使用现有单模型生成契约。

## 9. 预算与审计

确定性路由不产生额外Token，Java只为最终回答模型预占预算。以后启用LLM路由时，路由预算和回答预算必须分开预占、回报和结算。

至少记录：

- 请求的 `modelMode`。
- 最终实际使用的 `modelId` 和修订。
- 路由策略版本和原因编码。
- 候选快照摘要。
- LLM路由用量，若启用。
- 失败阶段：候选计算、路由、复核、预算或生成。

现有 `chat_message.model_id` 保存实际回答模型，不保存AUTO虚拟值。新增数据库字段前先核对现有会话、消息和Token用量表，避免重复建设通用运行表。

## 10. 失败与兜底

| 场景 | 处理 |
|---|---|
| 没有候选 | Java拒绝并提示联系管理员授权 |
| 只有一个候选 | 直接选中并记录原因 |
| LangChain无法判定 | 使用Java下发的授权兜底 |
| 返回候选外模型或错误修订 | Java拒绝执行 |
| 最终模型预算不足 | 拒绝生成，不切换到未预算模型 |
| 已经输出部分SSE | 禁止切换模型继续生成 |
| 供应商超时或限流 | 首期不静默跨模型重试 |

供应商故障后的跨模型切换涉及重复扣费、输出一致性和审计，另行设计。

## 11. 用户端交互

- 模型选择器增加独立的“智能选择”选项。
- AUTO状态保存为 `{ mode: 'AUTO', modelId: undefined }`。
- FIXED状态保存为 `{ mode: 'FIXED', modelId }`。
- Agent切换后重新校验可用模式和候选范围。
- AUTO回答完成后展示实际模型，例如“智能选择：模型A”。
- 历史消息展示当时实际使用的模型。

## 13. 验收标准

- FIXED请求不经过路由，行为与当前版本一致。
- AUTO只能选择用户和Agent共同允许的模型。
- 停用、未发布、配置不完整和上下文不足的模型不会进入候选。
- Python无法通过返回任意ID绕过Java权限。
- Java按最终模型完成上下文预算、Token预占和结算。
- 每条助手消息能追溯实际模型、修订和路由原因。
- RAG的Embedding/Rerank快照不受聊天AUTO影响。
- 路由失败、预算不足和生成失败只有一个明确终态。
- 旧客户端不传 `modelMode` 时继续按FIXED工作。

## 14. 结论

推荐路线：

```text
Java限定候选和权限
→ LangChain在候选内做确定性路由
→ Java复核最终模型并完成预算
→ 复用现有单模型生成链路
```

AUTO代码闭环、用户入口、本机数据库迁移和自动化验证已经完成。当前确定性路由不会额外调用模型；真实多供应商联调仍在项目最终环境验收阶段执行。
